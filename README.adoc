= Antora `example$` Kroki demo

A small, self-contained Antora project that demonstrates one authoring contract for PlantUML diagrams
that works for the *HTML site*, the *PDF export* and *standalone PlantUML tooling* from the same
sources:

* *Pages* reference a diagram source by Antora resource id: `+plantuml::example$order-model.puml[]+`.
  The id stays in AsciiDoc, where every consumer has the content catalog.
* *Diagram sources* (`.puml`) include each other with plain relative PlantUML includes:
  `!include ./layout/colors.puml`, `!includesub ./roles.puml!Core`, resolved against the including file
  as the PlantUML CLI and the JetBrains PlantUML plugin do. No Antora syntax inside PlantUML, so every
  `.puml` is a valid standalone diagram.
* `[plantuml]` blocks written directly in a page are for self-contained snippets. Diagrams with
  includes live in `.puml` files and are referenced by macro.
* A relative include starts with `./` or `../` (`!includesub ./sibling.puml!Part`, not
  `!includesub sibling.puml!Part`). asciidoctor-kroki 0.18 hands the target of an include inside an
  Antora resource unchanged to its adapter, which resolves a bare path against the `examples/` root,
  so a same-directory include without `./` silently disappears from the site's diagram; `../` forms
  work because Antora resolves them relative to the context file.

It accompanies https://github.com/asciidoctor/asciidoctor-intellij-plugin/issues/516[asciidoctor-intellij-plugin#516]
(IDE preview of such diagrams) and https://github.com/asciidoctor/asciidoctor-kroki/issues/519[asciidoctor-kroki#519]
(Antora resource ids and the Ruby gem).

== What it covers

`docs/modules/ROOT/pages/index.adoc` exercises, in order:

. *Block macro + shared-layout include* — `+plantuml::example$order-model.puml[]+`, whose `.puml`
  does `!include layout/colors.puml` and `!include layout/legend.puml`.
. *Reusing the shared layout* in a second diagram (`order-lifecycle.puml`).
. *`[plantuml]` delimited block* — a self-contained snippet without includes (the block rule).
. *`!includesub`* with a named sub-block — `!includesub roles.puml!Core`; the section itself includes
  the shared layout, so nested includes are resolved recursively.
. *Nested directories* — `nested/deep/order-nested.puml` reaches the shared layout and the roles library
  with `!include ../../layout/colors.puml` and `!includesub ../../roles.puml!Core`, the layout of a real
  diagram tree.
. *Pass-through* — `!include <C4/C4_Context>` cannot be resolved locally, so it is left untouched and
  resolved by the Kroki server. Remote `http(s)` includes are passed through the same way.

== Who resolves what

The Kroki server has no filesystem, so whoever sends a diagram must inline its includes first.

[cols="2,1,3"]
|===
| Consumer | Works | How

| Antora HTML site (`asciidoctor-kroki` JS 0.18.x)
| yes
| Resolves the macro target through the content catalog and joins the relative `!include`s against
  it (`antora-adapter.js` + `preprocess.js`). Nothing to add.

| Antora PDF export (Assembler → `asciidoctor-pdf -r asciidoctor-kroki`)
| yes, with `extensions/antora-assembler-kroki.js`
| The Ruby gem cannot see the catalog, so the extension exports the diagram sources to disk and points
  the macros at them; the gem's include preprocessor (2.0+) does the rest. See <<pdf-export>>.

| JetBrains PlantUML integration plugin, PlantUML CLI
| yes
| Plain relative includes; nothing Antora-specific in the `.puml` files.

| IntelliJ AsciiDoc plugin preview (Kroki renderer)
| yes, with the plugin branches below
| Two stacked plugin branches (superseding asciidoctor-intellij-plugin#2054): the first updates the
  plugin's embedded Kroki extension to the gem's 2.0 code, so relative `!include`s are inlined before
  the diagram is sent; the second resolves `example$` macro targets inside an Antora module and shows
  a placeholder with an open-in-editor link for anything that cannot render. See <<ide-preview>>.
  The release plugin (0.45.x) renders the diagrams without the shared layout.
|===

== Build

=== HTML site (Node only)

[source,sh]
----
npm install
npm run build
----

Open `build/site/index.html`. The PDF step of this command also runs if Ruby with `asciidoctor-pdf`
and the `asciidoctor-kroki` gem (2.0+) is on `PATH`; without Ruby, Antora logs the failed converter
and the site still builds.
The gem 2.0 line exists only as prereleases so far: `gem install asciidoctor-kroki --pre` (without `--pre`
you get 1.x, which sends the `!include` lines to the Kroki server unresolved, and the diagrams silently
lose their includes). The exported macro targets are absolute paths, so the converter must run in unsafe
mode (the `asciidoctor-pdf` CLI default) or `export_dir` must lie inside the Assembler's `build.cwd`.

=== HTML site + PDF (Docker, reproducible)

[source,sh]
----
npm run build:docker
----

Builds the image from the `Dockerfile` (Antora 3.2, `asciidoctor-kroki` 0.18.1, `@antora/pdf-extension`,
`asciidoctor-pdf`, `asciidoctor-kroki` gem 2.0.0.rc.3) and runs the playbook in it. The PDF lands at
`build/site/kroki-antora-example/_exports/index.pdf`.

[NOTE]
====
The build reads from `branches: HEAD`, so it needs at least one git commit. If you unzipped this
rather than cloning it, run `git init && git add -A && git commit -m init` first.

Diagram rendering needs network access to `https://kroki.io` (or change `kroki-server-url` in
`antora-playbook.yml` to a local Kroki server).
====

[[ide-preview]]
== IntelliJ preview

The IntelliJ AsciiDoc plugin does not depend on the asciidoctor-kroki gem; it embeds a copy. Two local
plugin branches bring the preview in line with the contract above; both supersede
asciidoctor-intellij-plugin#2054:

[cols="1,2,2"]
|===
| Plugin branch | What it adds | What to open here

| `feature/sync-kroki-extension-2.0` (build `0.45.7-kroki2.1`)
| Embedded Kroki extension updated to asciidoctor-kroki 2.0: PlantUML `!include`/`!includesub` resolved
  relative to the diagram file before sending, `kroki-plantuml-include-paths`, per-diagram error handling.
  No Antora awareness.
| `ide-demo/plain-includes.adoc` -- lives outside `docs/` (Antora ignores it) and references the `.puml`
  sources by document-relative path, so it isolates the include handling. Case 4 shows an inline block
  resolved via `kroki-plantuml-include-paths` set from `{docdir}`.

| `feature/kroki-antora-target-and-placeholder` (build `0.45.7-antora-placeholder.1`, stacked on the first)
| `plantuml::example$…[]` targets resolved inside an Antora module; a placeholder box with an
  *Open <file>* link (opens the `.puml` in the editor, where the PlantUML integration plugin previews it)
  whenever a diagram cannot render: unresolvable target, missing include file, or Kroki server error.
  The document attribute `kroki-preview-placeholder` shows placeholders for all Kroki diagrams without
  contacting the server.
| `docs/modules/ROOT/pages/index.adoc` -- the Antora page itself. All five macro diagrams render with
  the shared layout. Rename `examples/layout/colors.puml` and only the affected diagrams turn into
  placeholders naming the missing include.
|===

Comparison baseline: open either page with the release plugin (0.45.x). The diagrams render, but without
the shared layout, because the plugin sends the raw `.puml` text and the Kroki server silently drops the
includes it cannot read (black borders, white fill instead of blue borders, light fill and the legend box).

[[pdf-export]]
== PDF export and `example$` ids

`antora-assembler-pdf.yml` runs plain `asciidoctor-pdf -r asciidoctor-kroki`. Antora Assembler expands
`include::` directives and rewrites xrefs and images, then pipes the merged AsciiDoc to that Ruby
process, which knows nothing about Antora resource ids: `+plantuml::example$order-model.puml[]+` is not
a path to it.

`extensions/antora-assembler-kroki.js` (registered under `antora.extensions` in the playbook) closes
that gap on the Node side, where the content catalog is. It wraps the Assembler's page loading and,
only for Assembler exports, rewrites each page before it is merged: it writes the referenced resource
family — the module's `examples/` tree with its layout intact — to
`build/assembler-resources/<component>/<version>/<module>/<family>/` and points each macro at the
exported file. `asciidoctor-kroki` 2.0+ then resolves the relative `!include`s from that file's directory
itself; nothing Antora-specific reaches Ruby. This mirrors what the Assembler already does for `image$`
targets and is the behavior we would like the Assembler to grow natively, at which point the extension
retires. (An earlier proof of concept inlined the includes on the Node side instead; that mode was dropped
once the gem's preprocessor made it unnecessary.)

[source,yaml]
----
antora:
  extensions:
    - '@antora/pdf-extension'
    - require: ./extensions/antora-assembler-kroki.js
      export_dir: build/assembler-resources     # default, relative to the playbook dir; keep it outside the Assembler's build.dir (cleaned before conversion)
      macros: [plantuml, c4plantuml]            # default
----

Tests: `npm test` (`node --test`, no extra dependencies).
